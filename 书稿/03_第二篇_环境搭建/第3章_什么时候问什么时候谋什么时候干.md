# 第 3 章 什么时候问，什么时候谋，什么时候干

> 模式选错，AI 干得越快，你返工越狠。

先看我踩过的一个坑。

2025 年 11 月，一个周四下午四点，我接到一个活：把 47 份供应商 8D 报告（每份 8 到 15 页的 PDF）提炼成一张问题清单，周五上午十点要给部门经理过。

那会儿我用 WorkBuddy 才两周，正处在"什么活都直接丢给 Agent"的阶段。我把 47 个 PDF 拖进对话窗，说了一句话：

> 把这 47 份 8D 报告读一遍，提炼成一张问题清单，输出到桌面。

它跑了 11 分钟，交给我一份 47 行的表格。每行一份报告：供应商名、零件号、问题描述、整改措施。格式整齐，写得干净。

然后我发现我要的不是这个。经理要的是"这三年供应商的问题集中在哪几类"，按失效模式横向归类：绕线绝缘、轴承异响、漆层脱落、尺寸超差，每一类下面挂多少个案子、涉及哪几家供应商。它交的是纵向的，我要的是横向的。

我说"不对，我要按失效模式归类"，它又跑了一遍，给了第二版。第二版的问题是我没指定分类口径，它自己定了 9 类，其中"外观问题"和"表面缺陷"是同一件事拆成了两类，"其他"里塞了 14 个案子。

第三遍我才反应过来：这个活我一开始就没想清楚自己要什么，直接让 Agent 动手，等于让它在替我想。

第二天早上我重做了一遍。这次先切 Plan 模式，把同样的话说一遍，它先给我一份方案：分几步、分类口径怎么定、"其他"类超过百分之多少要拆、每一类要给几个数字。我在方案上改了三处，点头，它才动手。从说话到验收完，38 分钟。

第一遍三个版本加返工，3 小时 40 分钟。差了接近六倍。

这个差别跟模型聪不聪明没关系。同一个模型，同一个我，同一批文件。差别只有一件事：我在什么时候让它开始动手。

第 1 章讲过三种模式是什么、选择口诀怎么念。这一章讲日常：怎么切、切了以后上下文还在不在、干到一半怎么中断、出现什么信号说明该换了。最后一节 3.6，我拿一个真实任务把 Ask、Plan、Agent 从头到尾走一遍，每一步的提示词原文都给你。

## 3.1 三种模式的边界再确认

先把边界摆清楚。第 1 章给的是概念表，这里给操作表：你按下发送之后，它到底会碰什么东西。

| | Ask（问） | Plan（谋） | Agent（干） |
|---|---|---|---|
| 读你的文件 | 会读，只读 | 会读，只读 | 会读，也会写 |
| 改你的文件 | 绝不 | 绝不 | 会 |
| 跑程序 | 不会 | 不会 | 会 |
| 联网查东西 | 一般不 | 一般不 | 会 |
| 交出来的东西 | 一段回答 | 一份方案 | 改好的文件 + 汇报 |
| 一次交活耗时 | 几秒到一分钟 | 一到三分钟出方案 | 几分钟到几十分钟 |
| 出错代价 | 答错了，你没损失 | 方案错了，你改文字 | 它真改了你的文件 |
| 翻车后的恢复成本 | 零 | 零 | 看有没有备份 |

### 怎么切

> 【待补：界面路径，以实际版本为准】

不管界面长什么样，三种切法通用：

1. **对话输入框附近的模式选择器**，点一下换。这是最直观的。
2. **直接在话里说**。比如"先别动手，给我方案""你现在改成只读，别改文件"。它会照做。
3. **开新对话时先定调**。第一句就写"这个任务先只问不动手"，后面它就不会自作主张。

我自己的习惯是第三种。每个新任务开口第一句先把模式说死，比中途改要稳。

### 切换后上下文还在不在

这是最多人问错的问题。分两种情况：

**同一个对话窗口里切：上下文在。** 前面说过的话、它读过的文件、它已经摸出来的结论，全都还在。我有一次 Agent 干到一半，切 Ask 问它"你刚才为什么把第 4.7 节归到试验类"，它答得上来，还把依据的关键词复述了一遍。切回 Agent，它接着往下干，没重头再来。

**新开一个对话窗口：短时记忆清空。** 它不记得你上一个窗口聊了什么。但你的长期记忆还在，比如你的岗位、你们的表格格式习惯、你说过"报告表头照 2025 版"。第 6 章专门讲这层记忆。

由此得出一条规矩：**一个任务尽量在一个对话窗口里干完。** 不要开五个窗口各问一句，那样每个窗口里的它都是个刚入职的新人。

### 中断了怎么办

Agent 干活的时候，你随时可以叫停。叫停之后有三条后续：

| 你想要什么 | 你就这么说 |
|---|---|
| 把改动撤回 | "停下来，把刚才改的文件恢复原样。" |
| 想知道它干到哪了 | "停，汇报一下当前进度和已经改了哪些文件。" |
| 改要求重来 | "停，方向不对。改成……，从头再来。" |

我最常用的是第二条。看到它开始做一个我没让它做的事，先停、先问进度，比让它一路跑完再收拾要省事。

还有一条笨规矩，但我建议每个人都养：**让 Agent 改原始文件之前，先复制一份。** 复制一份只要三秒，能救你的场合不止一次。

### 模式不是"设置一次管一天"

很多人以为模式是个开关，早上设成 Plan，今天就一直 Plan。实际用法是动态的：一个大任务里面，你会来回切好几次。

3.5 节专门讲什么时候该切，3.6 节那个完整演示里，我在一个任务里切了四次。

## 3.2 Ask 模式的正确用法

Ask 是最被低估的模式。新手觉得它"啥也不干"，老手用它省的时间最多。

它真正强的场合有三个。

### 场合一：查资料、搞懂一个概念

你要搞懂一件事，而不是要一个文件。这类活 Ask 就够了，开 Agent 是浪费。

对话示例一（搞懂概念）：

> 我在看一份客户的技术需求文档，里面写"电机在 -40 到 85 摄氏度范围内需满足 Class C 功能等级"。
> 我不懂 Class C 是什么。用汽车零部件行业的语境解释一下这件事：
> 1. Class C 在常见的功能等级划分里是什么意思？跟 Class A、B 的区别在哪？
> 2. 如果达不到 Class C，工程上通常的后果是什么？
> 3. 要验证它，一般要做哪些试验？
> 别给我建议，先让我搞懂。

它给我的回答里有一句我记到现在：Class A 是坏了要出人命，Class B 是坏了车还能开回家，Class C 是坏了车得拖走。这种一句话讲清三层区别的能力，是它最值钱的地方。

### 场合二：不动任何文件的安全试探

这是我最推荐的用法，也是工程现场最该养成的习惯。

在你让 Agent 动手之前，先用 Ask 问一句"如果我让你做这件事，你会动哪些文件"。它不会真的动，但会把它的打算说给你听。你听完就知道它理解得对不对。

对话示例二（动手前的试探）：

> 桌面上有一个文件夹"2026Q1_试验数据"，里面有 214 个 CSV 文件和一个 Excel 汇总表。
> 先不要动任何文件，只回答我：
> 1. 如果我要你把这些 CSV 合并进汇总表，你会按什么键做匹配？文件名还是文件里的某一列？
> 2. 你打算改哪个文件？会新建文件吗？
> 3. 你认为这个活最容易出错的地方在哪？
> 4. 你觉得我还需要告诉你什么，你才能做对？

第四问是我后来加的，价值最高。它会反问你"文件名里的时间戳格式是统一的吗""汇总表里已有的行要不要保留"。这些问题你答完，Agent 阶段的返工基本就没了。

### 场合三：干完活之后的复盘和追问

Agent 交完活，别急着关窗口。切回 Ask 问两句：

- "你刚才为什么选这个分类口径？"
- "这 61 条任务里，哪几条你最没把握？"

第二句特别有用。它自己说没把握的地方，就是你验收时该重点看的地方。

### 好用法 vs 坏用法

| | 好用法 | 坏用法 |
|---|---|---|
| 提问方式 | 说清背景 + 列具体问题 + 限定回答范围 | "帮我看看这个"，附一个文件 |
| 提问数量 | 一次问 3 到 5 个编号问题 | 一句话问一个开放大问题 |
| 是否指明文件 | 给出路径、文件名、页数 | "那个报告" |
| 是否限定动作 | 明说"只读，不要改任何文件" | 不说，指望它自觉 |
| 拿到答案后 | 追问它没把握的地方 | 直接信，转头就干 |
| 搞懂之后 | 切 Plan 让它出方案 | 直接切 Agent 让它上手 |

最后一行的差别就是这一章开头的那个下午。

## 3.3 Plan 模式：怎么读懂它给的方案

Plan 模式下它交出来的是一份文字方案。你得会读，不然"看了方案点点头"就变成了走过场。

先看一份真实的方案长什么样。这是 3.6 节那个任务里，它给我的第一版方案（我删掉了两处重复描述，其余原文）：

```text
【拆分方案 v1】

目标产物：SOR_任务清单_某欧系平台_2026.xlsx，含 1 张总表 + 7 张职能分表

第一步 建立条款索引
  输入：SOR 全文
  动作：把全部 must/shall 条款编号 T001 起顺排，保留章节号与英文原文
  产出：内存中的条款表（此步不落盘）

第二步 职能分配
  分配口径：按条款关键词自动归类，一条款只归一个主责职能
  重叠条款：允许第二职能，标"协办"
  无法归类的：放进"待定"表，不猜
  产出：条款表新增三列（主责职能、协办职能、归类依据关键词）

第三步 条款转任务
  规则：一条 must/shall = 一条内部任务
  合并规则：同一职能、同一章节、语义相邻的条款可合并，合并后保留全部条款号
  产出：任务清单，字段如下
    任务编号
    来源条款号（如 4.2.3）
    条款原文（英文）
    中文解读（一句话）
    主责职能
    协办职能
    任务类型：设计 / 校核 / 试验 / 采购 / 文档
    交付物
    截止时间（用相对时间，如"SOR 回复前 7 天"）
    风险等级：高 / 中 / 低
    状态：待启动

第四步 风险标注
  依据：与本部门已量产平台的能力对比
  判为"高"的三种情况：超出已量产范围、需要新增试验设备、需要供应商重新报价
  产出：高风险任务列表，附在总表最前

第五步 输出文件
  用 openpyxl 写 xlsx，中文表头，冻结首行，按主责职能分表
  输出到桌面

本方案最容易出错的三处：
  1. 条款归类靠关键词，可能误判。规避：保留"归类依据关键词"列，方便你人工改
  2. 风险等级需要你们现有平台的能力数据，我没有。规避：默认标"待评估"，不编造
  3. 截止时间我不知道你们的排期。规避：用相对时间表达，不写具体日期

需要你确认的三件事：
  1. 全部条款都转任务，还是只转 must？
  2. 风险等级要我评估吗？要的话请给我现有平台的能力边界数据
  3. 截止时间用相对时间表达可以吗？

预计耗时：约 15 分钟
```

*图 3-3 看方案只看三处（作者根据公开资料绘制）*

### 看方案只看三处

一份方案可能有几百字，你不用逐字读。看这三个地方就够。

**第一处：第一步是不是你以为的第一步。** 起点错了，后面全白搭。上面这份方案的起点是"建立条款索引"，跟我想的一致。如果它第一步写的是"按职能拆成 7 个表"，那说明它把顺序搞反了，我要按职能发给人，但编号得先统一。

**第二处：中间有没有它替你做决定的地方。** 这类地方在方案里通常长这样："分配口径：按条款关键词自动归类""判为高的三种情况""合并规则：语义相邻的条款可合并"。每一处都是它在替你定规则。你要问自己：这条规则我认吗？

上面这份里，我最不认的是"风险等级"那一处。它没有我们现有平台的能力数据，判出来的高、中、低是猜的。

**第三处：最后一步交出来的东西是不是你要的形态。** 这一步最容易被忽略，也最容易返工。它说交"1 张总表 + 7 张职能分表"，我真正要的是 8 张表，多一张歧义条款表给客户电话会用。这个我在改方案时补上了。

看这三处，一份几百字的方案两分钟就过完了。

### 三条改方案的话术

改方案不用重写，说三句话就够。这三条是我用得最多的，直接抄。

**话术一，改局部，其余不动：**

> 第三步的任务编号规则改一下：改成"职能缩写-序号"，比如 NVH-001、ELE-002。
> 因为我要按职能把表拆开分别发给七个人，编号带职能更好认。其余不变。

关键是"其余不变"四个字。你不说，它可能把别的也改了。

**话术二，推翻它的一个默认：**

> 第四步的风险等级不要你评估，全部填"待评估"。
> 理由：你没有我们现有平台的能力数据，评估出来也是猜。
> 另外把"待评估"单独做一列，方便我筛选后人工过一遍。

给它理由，它下次就不会再犯同一个错。这条尤其适用于它编数据的场合。

**话术三，在末尾加一步：**

> 在第五步之后再加一步：额外输出一张"歧义条款表"。
> 字段：条款号、条款原文、歧义点、建议向客户提问的措辞（中英对照）。
> 这张表我要直接用在下周的客户电话会上。

加一步比改中间步骤安全，不会打乱它已有的逻辑。

改方案还有个原则：**一次说完，不要一次改一条。** 你把三条意见一口气给它，它一次改完；你一条一条给，它改三遍，每遍都要重读上下文。

## 3.4 Agent 模式：交活的完整动作链

Agent 是唯一会真动你文件的模式。它有一条完整的动作链：给活、盯、收、验。少一步都可能出事。

![图 3-4 Agent 交活四步动作链](../配图/svg/fig-3-4-agent-chain.svg)
*图 3-4 Agent 交活四步动作链（作者根据公开资料绘制）*

### 第一步：给活

一句话说清四要素：源文件、动作、输出形态、验收口径。缺一个，它就得猜。

```
源文件：桌面 / 2026Q1_试验数据 / 214 个 CSV，以及汇总表 summary.xlsx
动作：把 214 个 CSV 的数据合并进 summary.xlsx，按"样件编号 + 日期"匹配，已存在的行保留不动
输出形态：直接改 summary.xlsx，不要新建文件，改之前把原文件复制一份带 .bak
验收口径：合并后总行数、新增行数、匹配失败的行数，三个数字报给我
```

四要素里最常被漏掉的是**验收口径**。你不要它报数字，它就只说一句"已完成"，你还得自己打开文件数。

### 第二步：盯

交完活别离开。盯三个时间点的动静：

| 时间点 | 看什么 | 不对劲的表现 |
|---|---|---|
| 前 30 秒 | 它有没有先去找文件 | 直接开写，说明它没读源文件 |
| 第一次汇报 | 它理解的口径跟你一不一致 | 它复述的匹配键跟你说的不一样 |
| 中途汇报 | 有没有出现"我推测""应该是" | 出现就是它在猜，立刻叫停 |

我自己定了一条规矩：**Agent 干活期间，我在前两分钟内不离开座位。** 大部分翻车都发生在开头，开头看住了，后面基本稳。

### 第三步：收

它干完会汇报。收的时候拿走三样东西：

1. **产物清单**：它新建或改了哪些文件，路径是什么。
2. **它说的数字**：总行数、处理了多少、跳过多少。
3. **它自己承认没把握的地方**，一般在汇报最后一段，常常以"请确认"开头。

第三样最值钱。它主动说"第 47 行的数据格式和其他行不一致，我按 xx 处理，请确认"，这一句能替你省掉半小时的抽查。

### 第四步：验

这步是你的，谁也替不了。抽验比例我的习惯是：

- 条目少于 50 条，全查；
- 50 到 200 条，抽 10 条，其中至少 3 条是它说没把握的；
- 超过 200 条，抽 5%，另外全查它标"待定"的部分。

抽查的动作是回源文件核对，不是看它写得漂不漂亮。第 18 章会给一套完整的验收动作清单。

### 四步上的常见错误

| 步骤 | 常见错误 | 后果 | 补救 |
|---|---|---|---|
| 给活 | 没说验收口径 | 它只说"已完成" | 补一句"报三个数字给我" |
| 给活 | 让它直接改原始文件 | 改坏了没退路 | 要求先备份 .bak |
| 盯 | 交完活就去开会 | 它跑偏 20 分钟你不知道 | 前两分钟留在座位 |
| 收 | 只看它给的文件，不看汇报 | 漏掉它说的"请确认" | 汇报最后一段必读 |
| 验 | 只看格式对不对 | 数据错了你签字 | 回源文件抽验 |

### 信号一：它开始瞎猜

**表现**：它的回答里出现"通常""一般来说""可能是""我推测"，或者它开始编一个文件路径、一个标准号、一个你没给过的数字。

**真实场景**：2026 年 1 月，我让它整理一份材料的认证清单。它在 Plan 阶段写"该材料一般需要通过 xxx 认证"，那个认证编号我查了，不存在。我立刻切 Ask，问它"这个认证编号你是从哪份文件里看到的？"它承认是自己推的。

**该怎么办**：从 Plan 或 Agent 切到 Ask，让它交代信息来源。交代不出来的一律删掉。这是第 17 章"AI 的七宗罪"里的头一条。

### 信号二：它问的问题越来越多

**表现**：它反问你的次数超过三轮，而且问题越来越细，比如"这个文件里的日期格式是年月日还是月日年""表头算不算数据行"。

**真实场景**：同一个月，我让它把三份不同年份的试验大纲合并成一份。它问到第四个问题时我停了。它问的全是格式细节，说明它没搞懂这三份大纲的结构差异在哪。

**该怎么办**：切 Ask，让它先把结构讲给你听。你听完往往发现，问题不在格式，在于你自己还没决定"以哪一份为基准"。这个决定只能你做。

### 信号三：你已经改了三版

**表现**：同一个活，它交给你三个版本，你都不满意，而且每次改的都是同一类问题。

**真实场景**：本章开头那个 47 份 8D 报告的下午，就是标准案例。三版都不对，问题不在它，在我没说清分类口径。

**该怎么办**：立刻停手，切 Plan，让它从头出一份方案。注意是**从头出方案**，不是在第三版上继续改。在错的版本上打补丁，越打越乱。

### 信号四：任务做了一半发现方向不对

**表现**：它已经干到第三步、第四步了，你突然发现第一步的产物就不是你要的。

**真实场景**：2026 年 3 月，我让它把一份客户审核的整改项做成跟踪表。它干到第四步开始填责任人，我才发现它按"审核发现项"建的表，我要的是按"内部整改动作"建表。一个发现项可能对应三个整改动作。它已经填了 40 行。

**该怎么办**：叫停，切 Ask，让它汇报当前进度和已改的文件。然后判断：能不能在现有基础上改？能就给新指令继续；不能就让它回滚，重来。

那次我判断能改。我让它加一列"整改动作序号"，一个发现项拆成多行。它改了 6 分钟，比推倒重来快。

### 四个信号的对照表

| 信号 | 说明什么 | 切到哪 |
|---|---|---|
| 它开始瞎猜 | 信息不够，它在编 | 切 Ask，追来源 |
| 它问得越来越多 | 结构没摸清或你没定基准 | 切 Ask，让它先讲结构 |
| 你已经改了三版 | 你没说清需求 | 切 Plan，从头出方案 |
| 做了一半方向不对 | 起点就错了 | 先停，切 Ask 问进度，再决定改还是重来 |

## 3.6 一个真实任务走完三种模式 ★★★

这一节是本章的重点。我拿一个工程现场最常见也最烦的活，把三种模式从头到尾走一遍。每一步的提示词原文都在，你可以照抄。

**任务**：客户发来一份 68 页的技术需求文档（SOR），要求 10 个工作日内回复技术可行性。我要把它拆成一份内部任务清单，分给 7 个职能去认领。

**为什么这个活难**：文档是英文的，68 页里散落着 100 多条带 must、shall 的强制条款，有些条款之间有依赖，有些条款写得含糊。人工拆，我 2024 年干过一次同类活，两个人两天。

### 第一步：Ask 摸底（6 分钟）

我先不拆，先用 Ask 把这份文档摸清楚。摸底要拿到三个东西：文档结构、强制条款全集、歧义条款。

提示词原文：

```
这是一份客户技术需求文档（SOR），文件在桌面 / SOR_某欧系平台_2026.pdf，共 68 页。
先不要做任何修改，也不要生成任何文件，只回答我下面四个问题：

1. 这份文档一共有哪几个章节？列出章节号和标题。
2. 全文一共出现多少次 must、多少次 shall、多少次 should？分别统计数字。
3. 把所有含 must 或 shall 的条款挑出来，按章节号顺序列成一张表，包含：
   条款号、条款英文原文（不要翻译、不要改写）、所属类别。
   类别限这九种：性能、环境、寿命、电气、EMC、尺寸接口、文档交付、试验验证、其他。
4. 挑出你认为存在歧义的条款（定义不清、缺少边界条件、前后不一致），
   说明歧义具体在哪，以及它会影响哪些后续判断。

要求：
- 第 3 问的表格不许省略任何条款，数量以你实际统计为准。
- 如果你对某条条款的类别没把握，类别栏填"待定"，不要猜。
- 回答完先别给建议，我会接着问。
```

它给我的结果：

- 章节：11 个一级章节，从 1.0 范围到 11.0 交付物。
- 计数：must 出现 96 次，shall 出现 74 次，should 出现 38 次。扣除重复和说明性文字后，实际的强制条款是 127 条。
- 条款表：127 行，类别分布我记了下来，试验验证 31 条、性能 24 条、环境 19 条。
- 歧义条款：8 条。其中第 3 条我印象很深，原文大意是噪声应在背景噪声不高于 20 dB 的条件下测量，而我们台架的本底噪声是 28 dB。

Ask 阶段的第二问，只针对那条要命的歧义：

```
第 3 条歧义"噪声测量条件"这条，我们台架的本底噪声是 28 dB，达不到 20 dB。
帮我做两件事：
1. 在这份 SOR 全文里找一找，有没有别的地方对噪声测试条件做过补充说明？把原文抄给我，注明章节号。
2. 如果没有，把同样依赖"测试条件"这一前提的其他条款列出来，说明它们各自的测试条件要求。
```

它找了一遍，回答：全文没有其他补充说明；另有 6 条条款依赖测试条件，其中 2 条要求的也是 20 dB。

这一步的价值在于：我知道了这不是一条孤立的坑，是一个会影响 3 条条款的坑，得在客户电话会上专门问。

我承认，做这一步的时候我心里是急的。68 页的东西摆在那儿，十个工作日的期限挂在那儿，脑子里的声音一直在说"别问了，赶紧动手"。我强按着自己问完，是因为 2024 年那次人工拆分留下的教训：那次漏掉的 3 条条款，全都是因为没人先把条款点清楚。

这也是 Ask 摸底最容易被跳过的原因。它不产出任何文件，你看着屏幕上刷刷滚过去的回答，会觉得自己在浪费时间。实际上这 6 分钟买的，是后面每一步的地基。

还有一条规矩我在这一步定了：**must 和 shall 转任务，should 单列参考，不转。** 这不是它替我定的，是我定的。SOR 里 should 通常有 38 条，如果把 should 也转成必办项，任务清单会虚胖，7 个职能负责人拿到手会先骂人。这个判断只能人来做。

Ask 阶段结束，我手上有了三样东西：文档结构、127 条强制条款的清单、8 条歧义条款。全程 6 分钟，没动过任何文件。

### 第二步：Plan 出方案（12 分钟，含我改两轮）

切 Plan 模式。3.3 节那份方案就是这一轮出来的。提示词原文：

```
基于刚才 Ask 阶段的摸底结果（127 条 must/shall 条款、11 个章节、8 条歧义条款），
我要把这份 68 页的 SOR 拆成一份内部任务清单，分给 7 个职能去认领：
电机设计、NVH、热管理、电子控制、试验验证、采购、质量。

请给我一份完整的拆分方案，必须包含下面五项：
1. 分几步做，每一步做什么、产出什么。
2. 按什么口径把 127 条条款分配到 7 个职能，一条款涉及多个职能时怎么处理，
   归不了类的怎么办。
3. 每一条内部任务要包含哪些字段，逐项列出。
4. 最终输出文件的格式（我要一份能直接发给 7 个职能负责人的 Excel）。
5. 你认为这个方案最容易出错的三个地方，以及你的规避办法。

要求：
- 只给方案，不要执行，不要生成任何文件。
- 方案里凡是你需要我来定的事，单列一节"需要我确认的事"。
- 预计耗时也告诉我。
```

它给的方案就是 3.3 节那份。我按"看三处"的方法过了两分钟，改了三条。

改方案的话术原文（三条一次性给）：

```
方案我看了，改三条，其余不变：

1. 第三步的任务编号规则改一下：改成"职能缩写-序号"，比如 NVH-001、ELE-002。
   因为我要按职能把表拆开分别发给七个人，编号带职能更好认。

2. 第四步的风险等级不要你评估，全部填"待评估"。
   理由：你没有我们现有平台的能力数据，评估出来也是猜。
   另外把"待评估"单独做一列，方便我筛选后人工过一遍。

3. 在第五步之后再加一步：额外输出一张"歧义条款表"。
   字段：条款号、条款原文、歧义点、建议向客户提问的措辞（中英对照）。
   这张表我要直接用在下周的客户电话会上。

另外回答你"需要我确认的三件事"：
1. 127 条全部转任务，should 不转，但需要单独列一张 should 清单供参考。
2. 风险等级按我上面第 2 条处理，我不给你能力数据。
3. 截止时间用相对时间表达可以，但请统一按"SOR 回复前 N 天"的格式。

改完把新版方案给我，我还是先看，看完再让你动手。
```

它给了 v2 方案。v2 相对 v1 只动了三处，其余整段保留：

```text
【拆分方案 v2】相对 v1 的改动

改动 1（第三步）
  任务编号规则改为：职能缩写-序号
  示例：MOT-001（电机设计）、NVH-001、THM-001（热管理）、ELE-001（电子控制）、
        TST-001（试验验证）、PUR-001（采购）、QUA-001（质量）

改动 2（第四步）
  删除"风险等级判定"的全部逻辑。
  风险等级列统一填"待评估"，不再区分高中低。
  新增"待评估"筛选列（是 / 否），供人工过筛。

改动 3（新增第六步）
  第六步 输出歧义条款表
    数据来源：Ask 阶段挑出的 8 条歧义条款
    字段：条款号、条款原文（英文）、歧义点、建议向客户提问的措辞（中英对照）
    用途：客户电话会
  第七步 输出 should 参考清单
    字段：条款号、条款原文（英文）
    不转任务、不编号、不分配职能

其余（第一步、第二步、第三步合并规则、第五步输出格式）与 v1 一致，未改动。
预计耗时：约 18 分钟（比 v1 多 3 分钟，因为多了两张表）
```

v2 我只看了两个地方：一是它有没有把我没让它改的地方也改了，看下来没有，这点很重要；二是新增的第六步、第七步插在哪儿，看下来是排在第五步之后，没有打乱前面的顺序。看完我就点头了。

一个提醒：**改方案会让它重新算耗时。** v1 说 15 分钟，v2 说 18 分钟，后面 Agent 实际跑了 22 分钟。这三个数字一个比一个大，是正常的，别拿第一个数字去催它。

Plan 阶段 12 分钟，其中它出方案 4 分钟，我读加改 6 分钟，它改方案 2 分钟。

### 第三步：Agent 执行（22 分钟）

切 Agent 模式。这一步的关键是把 Plan 定下来的东西复述一遍，别让它自己发挥。

提示词原文：

```
按你给的拆分方案 v2 执行。源文件：桌面 / SOR_某欧系平台_2026.pdf。
输出文件：桌面 / SOR_任务清单_某欧系平台_2026.xlsx。

执行要求：
1. 任务编号用"职能缩写-序号"，如 NVH-001、ELE-002。
2. 风险等级全部填"待评估"，不要评估，不要编造。
3. 除总表和 7 张职能分表外，额外输出一张"歧义条款表"，
   字段：条款号、条款原文、歧义点、建议向客户提问的措辞（中英对照）。
4. 额外输出一张"should 参考清单"，不转任务，只列条款号和原文。
5. 归类不确定的条款放进"待定"表，标明不确定的原因，不要猜。
6. 改文件前把原位置同名文件备份为 .bak（如存在）。

过程要求：
- 每完成一步用一句话汇报，不要长篇。
- 遇到你判断不了的问题，停下来问我，不要自己决定。

完成后给我四个数字：
- 处理的条款总数
- 生成的任务总数
- 待定条款数
- 合并掉的条款数
```

**盯的过程**：它跑了 22 分钟，汇报了 5 次。前 30 秒它先去读了 PDF，这是对的。第 3 次汇报有一句我特意停下来看了：

> 第 4.7 节的 3 条条款引用了试验标准号，但文档里没有给出正文，我放进待定表，原因：无法判断试验条件。

这个处理是对的，我没干预。

**收的产物**：一个 xlsx，10 张表（总表、7 张职能分表、歧义条款表、待定表）。另外它在汇报最后写了两句"请确认"：一是第 4.7 节那 3 条，二是总表里有 4 条条款它认为同时属于性能和试验验证，它按主责归了性能、协办标了试验验证。

它还给了四个数字：条款总数 127、任务总数 61、待定条款 6、合并条款 66。

第一个数字跟我 Ask 阶段统计的 127 对上了，这是我最先看的一个数。

### 第四步：验收（15 分钟）

| 检查项 | 动作 | 结果 |
|---|---|---|
| 条款总数对不对 | 它报的 127 和 Ask 阶段的 127 对比 | 一致 |
| 条款号有没有抄错 | 随机抽 8 条任务，回 PDF 翻到对应章节核对条款号 | 7 条对，1 条错（它写 4.7.2，原文是 4.7.3） |
| 待定表有没有漏判 | 逐条看 6 条待定，人工判断能不能归 | 6 条里 2 条能归到 NVH，我手动移过去 |
| 歧义表能不能用 | 看 8 条歧义的"建议提问措辞"是否中英对照、是否可直接发 | 7 条可用，1 条措辞太生硬，我自己改了 |
| 职能分表能不能直接发 | 打开 7 张分表，看表头、看有没有空行 | 都能发，一张表里有一行协办栏为空，我补了"无" |

15 分钟，查出 1 个条款号错误、2 条待定误判、1 处措辞问题。

**全程时间**：Ask 6 分钟 + Plan 12 分钟 + Agent 22 分钟 + 验收 15 分钟 = 55 分钟。

对照我 2024 年那次人工拆分：两个人两天，而且那次的条款清单最后还漏了 3 条，是客户在电话会上提醒的。这次 127 条一条没漏。

### 对照：如果一上来就开 Agent

同一个任务，我第二天又拿另一份同类 SOR 试了一遍"直接开干"的做法，把过程记了下来，好让你看清差别在哪。

提示词只有一句："把这份 SOR 拆成内部任务清单，输出到桌面。"

它跑了 9 分钟，交给我一份 52 行的清单。问题有四个：

- 它把 should 也转成了任务，清单里混进了 21 条不必办的项；
- 它没有条款号，我无法回原文核对；
- 它按自己的理解定了 6 个职能，跟我们实际的 7 个对不上；
- 风险等级它照填了高、中、低，我问它依据是什么，它说"根据行业常见情况判断"。

我在这份 52 行的清单上改了 40 分钟，还是不能用，最后推倒重来。前前后后 49 分钟，产物作废。

差别不在它干得快不快，直接开干那次它只用了 9 分钟。差别在于：**没有 Ask 阶段的摸底，它不知道有 127 条条款这个数；没有 Plan 阶段的方案，它的分类口径、字段、职能划分全是自己定的。** 你没定的事，它就替你定，而定错了你只能在成品上改。

### 这一节的三条经验

**一，Ask 摸底的数字，是后面验收的基准。** Ask 阶段统计出 127 条，Agent 阶段它报 127，两个数字对上，我心里就有底了。如果你跳过了 Ask，你连"该有多少条"都不知道，验收就只能靠感觉。

**二，Plan 阶段改方案，比 Agent 阶段改文件便宜十倍。** 我在方案上改三条花了 6 分钟。如果这三条在 Agent 干完之后才发现，它得重跑，我得重新验收。

**三，凡是它说"请确认"的地方，都要看。** 它汇报里的两处"请确认"，正好对应我验收时查出的两个问题。它其实知道自己在哪儿没把握，你只要肯看最后一段。

## 3.7 如果你只做一件事

一个动作就够了：**每个新任务的第一句话，都以"先给我方案，我点头了你再动手"结尾。**

就这一句。它把 Ask 和 Plan 之间的门槛降到了零，也把 Agent 的启动权拿回到你手上。

我那个 3 小时 40 分钟的周四下午，和 38 分钟的周五早上，差的不是能力，是这一句话。

## 小白词典

**模式**：WorkBuddy 干活的三种委托方式。Ask 是问，只读不动文件；Plan 是谋，先出方案等你点头；Agent 是干，直接读写文件把活做完。

**上下文**：一段对话里聊过的全部内容，包括你说的话、它读过的文件、它已经得出的结论。同一个对话窗口里切换模式，上下文保留；新开窗口会清空。

**SOR**：Statement of Requirements，客户发给供应商的技术需求文档。写清了产品要满足什么、怎么验证、什么时候交。汽车零部件行业里，一份 SOR 几十页到几百页都有。

**must / shall / should**：SOR 里的强制程度标记。must 和 shall 是必须满足，should 是建议满足。拆任务时只把 must 和 shall 转成必办项，should 单独留作参考。

**条款**：SOR 里带编号的一条要求，比如 4.2.3。验收时回原文核对，靠的就是这个编号。

**歧义条款**：写得含糊、缺少边界条件、或者前后不一致的条款。它不会自己消失，必须在回复客户前问清楚。

**待定表**：归类不确定的条目单独放的一张表。它的作用是防止 AI 硬猜，把判断权留给你。

**8D 报告**：供应商质量问题整改报告的通用格式，八个步骤，从问题描述到永久对策到预防再发。每份 8 到 15 页是常见长度。

**失效模式**：零件或系统失效的具体形式，比如绕线绝缘击穿、轴承异响、漆层脱落。按失效模式归类问题，能看出毛病集中在哪儿。

## 你的岗位怎么用

**设计工程师**：拿到客户 SOR 或内部设计任务书，先用 Ask 让它列出全部强制条款和歧义条款，再切 Plan 出拆分方案。你验收的重点是条款号有没有抄错，抽 8 条回原文核对，两分钟的事。

**质量工程师**：整理供应商 8D 报告或审核整改项这一类活，最容易犯的错就是本章开头那个：没定分类口径就让 Agent 干。先切 Plan 把分类口径定死，再动手。分类口径写在方案里，比写在脑子里可靠。

**采购 / 供应商管理**：比价、资质核查这类活涉及联网和外部数据，交给 Agent 之前先用 Ask 问一句"你会动哪些文件、会不会联网"。确认无误再放行，避免它把你的询价底稿改了。

**试验工程师**：试验大纲合并、试验数据汇总这类活，先让 Ask 讲清三份文件的结构差异，你自己决定以哪一份为基准，再进 Plan。基准这件事 AI 替你定不了。

**项目经理**：你的活大多是"把一堆输入变成一张能发出去的表"。这种活的标准路线就是本章 3.6 那条：Ask 摸底拿数字，Plan 定字段和口径，Agent 出文件，最后你按 Ask 阶段的数字验收。

**研发主管**：把"先出方案再动手"写成团队规矩，写进你们的任务模板里。新人最容易犯的错就是直接开 Agent，你要拦的是这一下。

## 本章交付物

**模式决策卡**：一张贴在显示器边上就能用的判断流程。

**第一步，问自己一句：这个活我说明白了吗？**

- 说不明白，或者还没想清楚自己要什么 → 切 Plan，让它先出方案。
- 我只是想搞懂一件事，不要任何文件 → 用 Ask。
- 说明白了，而且活儿在文件里 → 继续第二步。

**第二步，问自己一句：它动到文件，我能接受吗？**

- 不能接受，或者还没备份 → 停在 Plan 或 Ask，先备份。
- 能接受 → 进 Agent。

**第三步，进 Agent 之后，四步动作链照做：**

1. 给活说清四要素：源文件、动作、输出形态、验收口径。
2. 盯：前两分钟不离开座位，看到"我推测""应该是"立刻叫停。
3. 收：拿走产物清单、它报的数字、它说"请确认"的地方。
4. 验：抽验（少于 50 条全查，50 到 200 条抽 10 条，超过 200 条抽 5%），回源文件核对。

**第四步，出现这四个信号立刻换模式：**

| 信号 | 动作 |
|---|---|
| 它开始瞎猜 | 切 Ask，追信息来源 |
| 它问得越来越多 | 切 Ask，让它先讲结构 |
| 你已经改了三版 | 切 Plan，从头出方案 |
| 做了一半方向不对 | 先叫停，切 Ask 问进度，再决定改还是重来 |

**怎么做**：把上面这四步抄在一张便签上，贴在显示器边框。用两周，它会变成本能。

## 本章金句

> 模式选错，AI 干得越快，你返工越狠。

> 你没想清楚自己要什么，就别让它动手，那是让它在替你想。

> 看方案只看三处：起点对不对、它替你定的规则你认不认、终点是不是你要的形态。

> 在方案上改一条花两分钟，在成品上改一条花二十分钟。

> 它主动说"请确认"的地方，就是你验收时该重点看的地方。

> 同一个活，先谋后干是 55 分钟，边想边干是 3 小时 40 分钟。
